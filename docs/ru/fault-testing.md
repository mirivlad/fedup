# FedUp — сетевые сбои и fail-closed

Этот тест относится только к изолированным Linux network namespace, не к рабочему VPN. Он не меняет маршруты, DNS и firewall основной машины.

## Зачем это нужно

Когда TUN исчезает при аварии клиента, Linux может автоматически выбрать другой, обычный маршрут. Поэтому одной настройки маршрутизации недостаточно: запрет на утечки должен сохраняться отдельно от процесса VPN.

## Что проверяем

Опциональный режим FEDUP_TUN_FAULT=1 в tests/tun-smoke.sh создаёт три изолированные сети: клиент, VPN-сервер и удалённый сервис. Затем добавляет **действующий прямой путь в обход VPN**. Сначала проверяется, что этот путь действительно работает. После этого устанавливается отдельная политика nftables в клиентском namespace: защищённые IPv4/IPv6 адреса разрешено достигать только через TUN.

После стандартных проверок IPv4/IPv6, TCP, UDP и DNS устанавливаются ограничения на внешнюю связь между клиентом и сервером: Linux tc netem добавляет 20 мс задержки в обе стороны, джиттер 5 мс и 1% случайных потерь. Через туннель передаются 192 КиБ двоичного TCP-трафика; выводится продолжительность одного прогона.

В конце отзывается сертификат, VPN-клиент аварийно завершается, а TUN исчезает. **При этом другой маршрут действительно существует**, но nftables должен запретить IPv4/IPv6-трафик к защищённым адресам. Сценарий работает для обоих транспортов: raw TLS и HTTP/2.

## Проверить на MX Linux / Debian

~~~bash
sudo apt install iproute2 iputils-ping nftables curl python3 \
  openssl libssl-dev pkg-config tcpdump
cd ~/git/fedup
git pull
cargo build --workspace
cargo test --workspace --all-targets

sudo env FEDUP_TUN_TRANSPORT=raw FEDUP_TUN_FAULT=1 bash tests/tun-smoke.sh
sudo env FEDUP_TUN_TRANSPORT=h2 FEDUP_TUN_FAULT=1 bash tests/tun-smoke.sh
~~~

Тест требует root для управления временными namespaces, nftables и tc. На основной сетевой конфигурации он не работает и не устанавливает постоянные правила.

## Чего это не доказывает

- Готового kill switch на пользовательском Linux: защита в тесте распространяется только на два конкретных лабораторных IP-адреса.
- Отсутствия DNS, IPv6, WebRTC или других утечек на компьютере.
- Безопасного публичного egress или устойчивости к смене мобильной сети.
- Обнаруживаемости либо необнаруживаемости настоящими ТСПУ или другими DPI.
- Преимущества одного транспорта по скорости: одиночные результаты не являются сравнительным бенчмарком.

Для рабочего VPN необходим привилегированный сетевой агент с отдельной политикой маршрутов и firewall, отказоустойчивой установкой и откатом. Недопустимо считать безопасность выполненной только потому, что маршрут исчезает вместе с TUN.

Смотри также [исследование Linux TUN](tun.md) и [настоящий HTTP/2](http2.md).

## Независимая установка политики

Ранее тест использовал встроенные в Bash правила nftables. Теперь он запускает отдельную Rust-программу **fedup-netguard** с проверяемой JSON-конфигурацией: она создаёт таблицу атомарно, не переписывает существующие правила и сохраняет защиту независимо от процесса туннеля. После аварии клиента тест проверяет политику, добавляет постороннее правило для проверки обнаружения изменений и допускает удаление только отдельной явной командой оператора. Подробности — в [документации netguard](netguard.md).
