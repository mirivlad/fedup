# FedUp: настоящий HTTP/2 — экспериментальный транспорт

## Зачем отдельная реализация

В первом TLS-транспорте FedUp отправлял собственные кадры напрямую в TLS. У него не было согласования ALPN, а значит, нельзя было считать такой поток HTTP/2 или обычным HTTPS.

В новом компоненте **fedup-h2-lab** используется реальный HTTP/2 (библиотека h2), ALPN "h2", TLS 1.3 и полноценный запрос HTTP/2 POST на фиксированный путь /fedup-lab/v1/duplex.

Сервер проверяет клиентский сертификат mTLS и операторский список разрешённых сертификатов. Приложение передаёт бинарные данные в HTTP/2 DATA, отправляет правильный ответ 200, обрабатывает закрытие stream и учитывает HTTP/2 flow-control окна. Это **настоящий прикладной HTTP/2**, а не подстановка значения h2 в ClientHello.

### Что ограничено

- Прослушивание и подключения разрешены **только на loopback**.
- Поддерживается только один фиксированный POST и один поток на соединение, остальные запросы получают 404.
- Размер тестового запроса ограничен 256 КиБ; передача в ограниченных чанках с резервированием окна.
- Клиент использует уже зарегистрированное устройство с зашифрованным приватным ключом PKCS#8.
- Отозванный сертификат блокируется при установлении новой сессии.
- Отдельный fedup-h2-lab выполняет бинарный echo, а **fedup-tun** теперь умеет передавать настоящие IP-пакеты через HTTP/2 в командах server-h2 / client-h2. Оба режима пока экспериментальные, без выхода в интернет.
- Сейчас HTTP/2-сервер ещё запрашивает клиентский TLS-сертификат, что тоже отличается от обычного публичного сайта. Требуется независимое исследование поведенческого профиля и безопасного прикладного подтверждения устройства.

## Проверить

~~~bash
cd ~/git/fedup
git pull
cargo build -p fedup-h2-lab -p fedup-identity -p fedup-enroll -p fedup-admin
cargo test --workspace --all-targets
bash tests/h2-smoke.sh
~~~

Скрипт сам создаёт временный CA, регистрирует экспериментальное устройство, запускает HTTP/2-сервер на 127.0.0.1 и проверяет обмен бинарными данными больше стандартного начального окна HTTP/2 (196608 байт). Затем отзывается разрешение на клиентский сертификат и проверяется отказ новому подключению.

## Что это доказывает, а что нет

Такой стенд доказывает, что Fedora/Linux-сервер и клиент FedUp могут обмениваться данными **внутри корректного HTTP/2 сеанса**. Он **не доказывает**, что сетевой наблюдатель перепутает FedUp с Firefox, Chromium или массовым видеосервисом.

Обнаруживаемые отличия всё ещё могут включать:
- ClientHello rustls и его порядок расширений, наборы шифров, SNI и ALPN;
- объёмы и интервалы TLS records;
- длительный двусторонний POST-stream вместо обычной короткой загрузки страницы;
- выбор IP/ASN, частоту подключений, паттерны потерь и реакцию на сетевые сбои.

Нет оснований обещать «невидимость для РКН». Настоящая цель — **измерить и уменьшить непреднамеренные различия**, сохранив стандарты и безопасность.

## IP-туннель поверх HTTP/2

Проверенный в GitHub Actions эксперимент:

~~~bash
cargo build -p fedup-tun -p fedup-identity -p fedup-enroll -p fedup-admin
sudo env FEDUP_TUN_TRANSPORT=h2 bash tests/tun-smoke.sh
~~~

Сценарий создаёт три отдельных Linux network namespace и запускает fedup-tun server-h2 / client-h2, затем проверяет IPv4/IPv6, TCP, UDP и синтетический DNS. После отзыва сертификата связь с удалённой сетью прекращается. Никаких глобальных маршрутов, системного DNS или NAT на основном ПК тест не меняет.

**Результат:** в GitHub Actions run 42570359233 тест прошёл, а извлечение ClientHello из PCAP подтвердило ALPN h2 вместо отсутствующего ALPN старого TLS-режима.

Приложение использует POST /fedup-lab/v1/ip-tunnel и передаёт FedUp-кадры в тело HTTP/2 DATA с ограниченным буфером и использованием WINDOW_UPDATE. Это полноценный HTTP/2, но до настоящего браузерного профиля и эксплуатационной надёжности ещё далеко.

## Следующее

1. Проверить HTTP/2 поток под высокой нагрузкой, с разрывами и нестабильной связью, а также по активным неверным запросам.
2. Доработать протокол авторизации, чтобы иметь возможность в будущем отказаться от необычного для большинства сайтов клиентского TLS-сертификата без ослабления идентификации устройств.
3. Доработать и стабилизировать уже существующий HTTP/2-транспорт TUN: потери сети, повторное подключение, задержки TCP-в-TCP, управление привилегиями и утечками.
4. Сравнить HTTPS/2 с реальными браузерами на одинаковых задачах, подготовить независимую контрольную выборку.
5. Рассмотреть HTTP/3/QUIC и стандартные методы туннелирования datagram, в частности RFC 9297/9298, не выдавая частную реализацию за совместимую с ними.

RFC 9113: https://www.rfc-editor.org/rfc/rfc9113.html

RFC 9297: https://www.rfc-editor.org/rfc/rfc9297.html

RFC 9298: https://www.rfc-editor.org/rfc/rfc9298.html
