# FedUp — регистрация устройства по логину и паролю

Текущий этап: **регистрация пользователя и телефона без ручного CSR/PEM**. Android получает публичный CA по проверенному HTTPS, создаёт неэкспортируемый ключ внутри Android Keystore, подписывает CSR, предъявляет логин и пароль и автоматически устанавливает выданный сертификат.

**Это ещё не публичный или повседневный VPN.** Подпись временно работает только в явно небезопасном лабораторном режиме с отдельным одноразовым CA. VPN-сервер всё ещё ограничен синтетическими IPv4/IPv6-адресами и должен запускаться в изолированном Linux network namespace. Обычный интернет и DNS этим режимом не защищаются.

## Управление пользователями

~~~bash
cd /path/to/fedup
cargo build -p fedup-users -p fedup-auth -p fedup-tun

./target/debug/fedup-users init ./target/fedup-accounts-lab
read -r -s -p 'Пароль от 12 байт: ' FEDUP_PASS; echo
printf '%s\n' "$FEDUP_PASS" |
  ./target/debug/fedup-users add ./target/fedup-accounts-lab vladimir --password-stdin
unset FEDUP_PASS

./target/debug/fedup-users list ./target/fedup-accounts-lab
./target/debug/fedup-users devices ./target/fedup-accounts-lab vladimir
./target/debug/fedup-users disable ./target/fedup-accounts-lab vladimir
./target/debug/fedup-users enable ./target/fedup-accounts-lab vladimir
~~~

Для существующей лабораторной базы перед переходом используется команда:

~~~bash
./target/debug/fedup-users migrate ./target/fedup-accounts-lab
~~~

Пароли в базе сохраняются только в форме Argon2id PHC-хешей с индивидуальной солью. У учётной записи есть номер ревизии: блокировка, повторное включение или смена пароля изменяют его. Сертификаты прежней ревизии автоматически перестают проходить проверку допуска.

Можно отозвать и отдельное устройство по отпечатку сертификата:

~~~bash
./target/debug/fedup-users revoke-device ./target/fedup-accounts-lab ОТПЕЧАТОК_SHA256
~~~

Список устройств хранит отпечаток SHA-256, принадлежность пользователю, срок действия и статус. Одновременно разрешается максимум восемь устройств на пользователя.

## API

Обычный безопасный для учётных данных режим:

~~~bash
./target/debug/fedup-auth serve ./target/fedup-accounts-lab 47677 --behind-https-proxy
~~~

Он умеет только проверять пароли. Для **одноразового изолированного опыта с заведомо тестовым CA**, и исключительно при осознанном согласии администратора, есть другой режим:

~~~bash
./target/debug/fedup-auth serve-enroll-lab ./target/fedup-accounts-lab \
  47677 ./test-ca.pem ./test-ca.key localhost --unsafe-lab-online-ca
~~~

Нельзя использовать в этой команде корневой CA настоящей инфраструктуры. Ключ \`test-ca.key\` — приватный PKCS#8 P-256 файл (режим 0600). В этом лабораторном процессе он находится в памяти сервиса, поэтому **не годится для боевого сервера**. В будущем нужен отдельный минимально привилегированный издатель и ограниченный промежуточный CA.

API привязан строго к 127.0.0.1, публичный доступ допускается только через отдельно настроенный HTTPS с настоящим сертификатом и дополнительной защитой от перебора:

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | /api/fedup/v1/login | Проверить пользователя, ответ 204 или 401 |
| GET | /api/fedup/v1/config | Получить публичный CA, имя сервера и отпечаток |
| POST | /api/fedup/v1/devices | После проверки пароля подписать CSR и связать устройство с пользователем |

Последний запрос принимает \`username\`, \`password\`, \`device\`, \`csr_pem\` и возвращает \`certificate_pem\`, \`ca_pem\`, \`ca_sha256\`, \`server_name\`, \`fingerprint_sha256\`, \`expires_at\`. Сертификат действителен максимум семь дней. При потере ответа повторный запрос с **тем же CSR** возвращает тот же сертификат. Новый или чужой CSR с уже занятым именем устройства отклоняется.

Пример Caddy для **выделенного тестового HTTPS-домена**, не готовый к боевому деплою:

~~~caddyfile
vpn.example.com {
    @fedup_api {
        path /api/fedup/v1/login /api/fedup/v1/config /api/fedup/v1/devices
    }
    reverse_proxy @fedup_api 127.0.0.1:47677
    respond 404
}
~~~

Не выставляйте 47677 напрямую в интернет и не подключайте эксперимент к действующей CA. Нужны полноценный журнал аудита, безопасный менеджер ключей, управление ролями, системная изоляция процесса, резервирование и управление квотами.

## VPN-сервер с учётными записями

В контролируемом Linux namespace вместо файлового allowlist доступен режим:

~~~bash
fedup-tun server-h2-accounts PRIVATE_IP:7443 futserver \
  test-ca.pem server.pem server.key ./target/fedup-accounts-lab
~~~

Он сначала проверяет подпись клиентского сертификата доверенным CA, затем требует, чтобы отпечаток был в базе как действующее устройство **действующего пользователя с правильной ревизией**. Во время сеанса повторно проверяет доступ примерно каждые пять секунд. Отзыв сертификата или блокировка учётной записи прекращают действующий туннель при очередной проверке.

## Android

На главном экране достаточно **сервера, логина и пароля**: нажатие «Войти и зарегистрировать телефон» автоматически получает CA по стандартному HTTPS, генерирует ключ P-256 в Android Keystore, создаёт подписанный PKCS#10 CSR и импортирует ответ сервера. Приватный ключ не передаётся. Прежние операции с вручную передаваемыми файлами оставлены в расширенной диагностике.

После регистрации приложение честно сообщает, что сертификат установлен, но не заявляет защиту всего интернет-трафика. Для передачи пакетов есть лишь отдельный лабораторный режим с ограниченным набором адресов и явным согласием Android. На физическом Android телефон с новым API ещё не испытан.

## Проверка

~~~bash
cargo test --workspace --all-targets
bash tests/users-smoke.sh
bash tests/users-enroll-smoke.sh
~~~

Последний сценарий использует **одноразовую SQLite-базу и временный CA**, проверяет правильный и неправильный пароль, подтверждение владения приватным ключом CSR, подпись сертификата, стабильный повторный ответ и блокировку старого сертификата после отзыва пользователя. GitHub Actions отдельно собирает Android debug APK.

## Что ещё требуется до VPS

- Защищённый издатель с промежуточным сертификатом и контролируемым доступом вместо временного CA в веб-сервисе.
- Механизм безопасного продления короткоживущих сертификатов и смены пользователя на телефоне без потери данных.
- Автоматическая настройка адреса VPN-сервера, защищённого сокета, полной маршрутизации IPv4/IPv6, DNS и системной политики Android Always-on/Lockdown.
- Испытания на настоящем телефоне и тестовом VPS, проверка отказов/блокировок и подписанного обновляемого APK.

Релиз и реальный сервер **не запускаем до приёмки этих пунктов**.
