# FedUp — одноразовые приглашения для устройств

Добавлен компонент **fedup-enroll**. Это первая версия выдачи клиентских сертификатов по приглашению. Она работает **офлайн**, на компьютере администратора, и пока **не является готовой системой автоматической регистрации через мобильное приложение**.

## Как устроена регистрация

1. Администратор создаёт приглашение для определённого устройства, например phone. Приглашение содержит одноразовый случайный токен, срок действия до 24 часов, публичный сертификат центра доверия и имя сервера.
2. Клиент создаёт собственный закрытый ключ **на своём устройстве**, в безопасном хранилище, и подписывает запрос CSR.
3. Клиент формирует файл запроса по приглашению и передаёт его администратору.
4. Администратор проверяет приглашение и CSR, после чего выпускает клиентский сертификат. Приватный ключ клиента для этого **не нужен**.
5. Администратор добавляет сертификат в список разрешённых устройств через fedup-admin.
6. Клиент получает готовый публичный сертификат. Доступ можно отозвать по имени устройства.

Приглашение можно погасить только один раз. Состояние хранится в SQLite на компьютере администратора, а не в публичном VPN-сервере.

## Проверка на твоём Linux

~~~bash
cd ~/git/fedup
git pull
cargo build -p fedup-enroll -p fedup-admin
cargo test --workspace --all-targets
bash tests/enroll-smoke.sh
~~~

Сценарий автоматически создаст временные тестовые ключи, пригласит устройство, выпустит сертификат, проверит его с OpenSSL, убедится в запрете повторной выдачи и затем отзовёт доступ. Вся тестовая информация удалится после завершения.

## Команды администратора

Создать приватный каталог учёта приглашений:

~~~bash
target/debug/fedup-enroll init /secure/offline/fedup-issuer
~~~

Создать приглашение для телефона сроком на 15 минут:

~~~bash
target/debug/fedup-enroll invite /secure/offline/fedup-issuer phone 900 \
    /secure/offline/ca.pem localhost phone-invite.json
~~~

На стороне клиента, при наличии CSR, сформировать заявку:

~~~bash
target/debug/fedup-enroll request phone-invite.json phone.csr.pem phone-request.json
~~~

На компьютере администратора подписать запрос:

~~~bash
target/debug/fedup-enroll approve /secure/offline/fedup-issuer \
    /secure/offline/ca.pem /secure/offline/ca.key \
    phone-request.json phone-cert.pem --unsafe-lab-plaintext-ca
~~~

Затем разрешить устройству подключаться к серверу:

~~~bash
target/debug/fedup-admin add /etc/fedup/allowed.txt phone phone-cert.pem
~~~

Если сертификат уже был выдан, но файл потерялся, можно повторно экспортировать **тот же самый** сертификат:

~~~bash
target/debug/fedup-enroll recover /secure/offline/fedup-issuer INVITATION_ID recovered.pem
~~~

## Важные ограничения

Всё выше — **экспериментальная реализация**. Пока клиент сам должен предоставить CSR; автоматическое создание ключа в Android Keystore, Windows и Linux Keyring ещё впереди. Сервис не принимает и не сохраняет клиентские закрытые ключи.

В тестовом сценарии используются временные незашифрованные ключи, которые сразу удаляются. **Не копируй этот способ хранения в реальную инфраструктуру.** Использование незашифрованного CA-ключа теперь требует явного флага --unsafe-lab-plaintext-ca. Это допустимо только на одноразовом стенде, не в рабочей инфраструктуре. Механизм безопасного разблокирования CA-ключа ещё предстоит реализовать.

Список регистрации не нужно и нельзя переносить на VPS. На VPS со временем останутся только публичные сертификаты доверия и необходимые серверные ключи. Передача файла приглашения должна происходить по доверенному каналу: получивший токен злоумышленник может попытаться зарегистрироваться раньше владельца.

Следом нужны полноценное создание и хранение ключей в клиентах, автоматическая доставка CSR и сертификата, подтверждение личности устройства и обновление сертификатов.
