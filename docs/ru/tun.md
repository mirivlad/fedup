# FedUp: Linux IP-туннель и исследования DPI

## Что реализовано

В FedUp появилась программа fedup-tun. Она открывает Linux TUN и передаёт IPv4/IPv6-пакеты как Datagram-кадры нашего протокола через взаимно аутентифицированное TLS 1.3-соединение.

Это **лабораторный IP-туннель, а не рабочий VPN с доступом в интернет**. Во избежание случайной эксплуатации разрешены только клиент 10.77.0.2 / fd42:fed0::2, VPN-сервер 10.77.0.1 / fd42:fed0::1 и **один внешний лабораторный узел** 10.88.0.10 / fd42:fed1::10. Встроенного NAT, автоматической системной настройки DNS, маршрута по умолчанию и полноценного kill switch пока нет. Синтетический DNS-запрос в третьей сети работает, но не меняет DNS-конфигурацию компьютера.

В тесте используются три временных Linux network namespace: клиент, VPN-сервер и отдельный удалённый сервис. Внешний клиентско-серверный veth имеет адреса 172.31.44.2 и 172.31.44.1; удалённый узел доступен только через сервер. Маршруты основного компьютера, firewall и DNS скрипт не меняет.

Сквозные проверки:
- IPv4 ping через TUN;
- IPv6 ping через TUN;
- HTTP/TCP через внутреннюю IP-сеть;
- передача UDP-датаграммы;
- отзыв устройства и разрыв действующего сеанса;
- настоящая маршрутизация IPv4/IPv6 до удалённого узла в третьем namespace;
- удалённый HTTP/TCP, UDP и синтетический DNS по UDP/53;
- отказ в отправке пакетов к посторонним адресам;
- отзыв сертификата разрывает доступ к удалённой сети;
- отсутствие маршрута в обычный интернет в **изолированной** тестовой сети.

## Запуск на Debian или MX Linux

Требуются rustc/cargo, Python 3, OpenSSL и заголовки OpenSSL, iproute2, iputils-ping, curl. Для захвата трафика также понадобится tcpdump.

~~~bash
cd ~/git/fedup
git pull
cargo build -p fedup-tun -p fedup-identity -p fedup-enroll -p fedup-admin
cargo test --workspace --all-targets
sudo bash tests/tun-smoke.sh
~~~

Для использования TUN в лаборатории нужны права root. Скрипт сам создаёт и уничтожает временные namespaces. **Пока не развёртывай fedup-tun на своём VPS.**

## Что показывают сетевые отпечатки

У текущего FedUp поверх TLS 1.3 работает собственная передача кадров. Реального протокола HTTP/2 или HTTP/3 пока нет; не объявляем клиент браузерным HTTPS и не подставляем фиктивное ALPN h2.

В изолированном тесте можно сделать PCAP и сравнить:
- FedUp на порту 7443;
- контрольное соединение curl → OpenSSL TLS 1.3 с настоящим HTTP/1.1 на порту 9443.

~~~bash
mkdir -p target/fedup-profile
sudo env FEDUP_CAPTURE_PCAP="$PWD/target/fedup-profile/lab.pcap" bash tests/tun-smoke.sh
sudo chown "$(id -u):$(id -g)" target/fedup-profile/lab.pcap
python3 tools/traffic-profile.py target/fedup-profile/lab.pcap \
  --output target/fedup-profile/report.json
cat target/fedup-profile/report.json
~~~

Скрипт на Python не обращается к сети и не расшифровывает TLS. Он читает синтетический PCAP, извлекает поля открытого ClientHello (включая SNI и ALPN, если они есть), размеры и время TCP-кадров. Контрольный curl — **не эквивалент современного браузера** и тем более не модель российских ТСПУ.

Пока **невозможно утверждать, что FedUp не обнаруживается DPI**. Наблюдатель всё ещё видит IP адрес назначения, ClientHello и временной профиль соединения. Устойчивость к блокировке целых IP/ASN другой вопрос, который одним транспортом не решить.

**Не публикуй дампы реального пользовательского трафика и действующие серверные конфигурации**. Все встроенные тесты выполняются на временных ключах и адресах.

## Следующие технические этапы

1. Отдельная испытательная выходная сеть и управляемый IP forwarding/NAT, затем безопасная маршрутизация на Linux без утечек.
2. DNS, IPv6 policy, kill switch, восстановление после падения и смены сети.
3. Транспорт с настоящей стандартной HTTP-семантикой, измеряемый против релевантного HTTPS-трафика. TLS поверх TCP для UDP внутри туннеля имеет задержки при потере пакетов.
4. Клиенты Android и Windows; SSH-администрирование и выпуск сертификатов остаются отдельными службами.

Смотри также английское описание в docs/tun.md и ADR-0006.

## Первый фактический отчёт (CI, 9 ноября 2026)

В изолированной сети сравнили один ClientHello FedUp и один контрольный ClientHello curl/OpenSSL:

| Поле | FedUp TLS | HTTPS HTTP/1.1 |
| --- | --- | --- |
| SNI | localhost | localhost |
| ALPN | отсутствует | http/1.1 |
| Размер ClientHello | 223 байта | 1561 байт |
| Количество предложенных cipher suite | 9 | 30 |
| Число TCP-кадров в конкретном тесте | 103 | 20 |

Команды передавали **разную нагрузку**, поэтому число кадров, длительность и интервалы нельзя сравнивать как доказательство классифицируемости. Но разницу в форме ClientHello и отсутствии ALPN можно зафиксировать независимо от полезной нагрузки.

Отчёт с самими извлечёнными полями находится в журнале GitHub Actions run 42563767605. Это одно лабораторное измерение, не проверка ТСПУ/РКН и не вывод о вероятности обхода блокировок.

Последний вывод: одной настройки ALPN недостаточно — нам нужен настоящий стандартный транспорт со своей корректной HTTP-семантикой и повторяемый контрольный эксперимент на сопоставимых нагрузках.

## HTTP/2

Теперь [настоящая HTTP/2-лаборатория](http2.md) интегрирована с fedup-tun в экспериментальных режимах server-h2 / client-h2. В отличие от первоначального TLS-режима, здесь действительно работают HTTP/2 POST, DATA, ALPN h2 и flow control. Полный трёхсетевой стенд с IPv4/IPv6, TCP, UDP и DNS прошёл в CI. Запуск: `sudo env FEDUP_TUN_TRANSPORT=h2 bash tests/tun-smoke.sh`.

Рабочего маршрута в интернет, защиты пользовательского ПК от утечек и доказанной незаметности для DPI по-прежнему нет.
