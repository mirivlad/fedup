# FedUp Lab — измерения Linux TLS/HTTP2 на tomas, 10 ноября 2026

## Лаборатория

Испытания выполнены в отдельном Docker Engine по адресу /home/mirivlad/lab на tomas. Использовались изолированные Linux network namespaces: Linux VPN-клиент, синтетический VPS с Caddy → h2c → FedUp, независимый клиент HTTPS-проб и синтетический HTTP/DNS интернет. Внешние хосты не тестировались. Тестовый публичный TLS-порт — 7443, не 443. Android не участвовал.

Варианты клиента: старый Linux Rustls и новый экспериментальный Linux OpenSSL TLS 1.3, сохраняющий проверку CA, имени TLS-сервера, HTTP/2 ALPN и подписанную авторизацию устройства. Обоим предлагается SNI localhost и ALPN h2,http/1.1. Контроль: восемь независимых curl/OpenSSL HTTPS/2 GET к тому же серверу, с проверкой тестового CA и тем же TLS 1.3.

## Изменение ClientHello

| Linux клиент | Длина ClientHello | Cipher suites | Совпадающие статические поля с curl |
| --- | ---: | ---: | ---: |
| Rustls, исходный app-proof | 241 Б | 9 | 8 / 17 |
| OpenSSL, первый вариант | 512 Б | 4 | 15 / 17 |
| OpenSSL, после исправления расширений | **512 Б** | **4** | **17 / 17** |

Расширения session_ticket и post_handshake_auth изначально давали два отличия от обычного curl/OpenSSL. После применения штатного OpenSSL NO_TICKET и объявления поддержки TLS post-handshake auth различия в измеряемых статических полях исчезли. TLS-проверка цепочки и имени сервера НЕ отключалась; реальная авторизация устройства по подписи оставлена без изменений.

В семи независимых сетевых прогонах после исправления (отметки 13:55:44, 14:01:14, 14:01:29, 14:01:43, 14:08:51, 14:17:35, 14:22:02 по времени PCAP на 10.11.2026) получено 17/17 совпадающих полей. Проверены размер и порядок cipher suites, набор и длины расширений, supported_groups, signature_algorithms, supported_versions, key_share groups/sizes, SNI, ALPN и другие статические элементы. Случайные байты client_random, session ID и ephemeral key share намеренно не сравниваются как постоянные: у корректных TLS-соединений они различны.

Все сквозные сетевые тесты с OpenSSL прошли: подписанный вход, TUN, IPv4 NAT, HTTP, UDP DNS, активные проверки в отдельном Linux-клиенте, запрет второго TUN и отзыв доступа.

## Следующее отличие: зашифрованный HTTP/2-поток

Для независимого контроля длительности сделан нормальный HTTP/2 streaming на Caddy: выдача порций данных через обычный HTTP/1.1 chunked upstream в течение примерно 5 секунд. Сделано три пары PCAP streaming/VPN (14:08:51, 14:17:35, 14:22:02).

| Признак | HTTPS/2 streaming | FedUp app-proof |
| --- | ---: | ---: |
| Медиана наблюдаемой длительности, мс | 4629,2 | 5027,3 |
| Первые зашифрованные TLS-записи клиента, байт | 53, 81, 67, 26 | 53, 41, около 690, около 200 |
| Зашифрованных TLS-записей клиента в сеансе | 4 | 10–11 |

**Длительность приблизительно сопоставима, однако нагрузка по количеству и направлению переданных байт всё ещё различается.** Поэтому это описательные измерения, а не измерение вероятности обнаружения. Видимое отличие 81 против 41 байта у второй зашифрованной записи может быть связано с разной отправкой HTTP/2 preface/SETTINGS у curl/nghttp2 и Rust h2. Содержимое TLS не расшифровывалось.

Проверен вариант клиентского HTTP/2 Builder с отключённым server push, увеличенными окнами и лимитом заголовков. Первые зашифрованные TLS-записи всё равно остались 81 у curl против 41 у FedUp. **Неэффективная настройка отменена** коммитом e31040d и сквозной VPN проверен снова. Искусственные задержки и padding пока не применялись: без разнообразных HTTPS-контролей это может только добавить предсказуемый отпечаток.

## Проверки и ограничения

- После отмены H2-тюнинга [CI #302](https://github.com/mirivlad/fedup/actions/runs/42833068704): 7/7 успешных заданий. Новые Python unit tests отдельно проверяют парсер TLS, статическое сравнение, работу с усечёнными данными и отсутствие ложных различий 404 из-за меняющегося Date у HEAD.
- Нет сведений о точности DPI (TPR/FPR). Нельзя приравнивать совпадение ClientHello с curl к полной неотличимости VPN от браузера.
- Данных о Firefox/Chromium, Android, публичном TCP 443, долгом двустороннем обычном HTTPS и работе реального блокировщика нет.
- PCAP включают только тестовые адреса и одноразовые учётные данные, сохранены на tomas. Не публиковать произвольные личные сетевые захваты.
