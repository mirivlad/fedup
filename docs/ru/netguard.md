# FedUp Netguard — независимая политика nftables

**Статус: лабораторный прототип Linux, не устанавливать на рабочую систему.**

Netguard — отдельная команда fedup-netguard. Она запускается с привилегиями root только внутри **специально созданного Linux network namespace**, применяет запрет выхода к указанным защищённым IPv4/IPv6-хостам вне TUN-интерфейса и запрещает обычный DNS (UDP/TCP 53) вне TUN.

В отличие от проверки «нет маршрута по умолчанию», правило **остаётся в ядре после завершения netguard и после аварии VPN-клиента**. Даже если Linux выбирает действующий прямой путь, пакеты к защищённым хостам должны блокироваться. Правила nftables привязаны к network namespace и по умолчанию не переживают его уничтожение или перезагрузку. Это ещё не постоянный системный сервис.

## Гарантии и границы реализации

- Проверка /proc/self/ns/net и /proc/1/ns/net: в исходном пространстве имён запуск с изменением firewall запрещён. Это экспериментальное ограничение, не универсальная sandbox-защита.
- JSON с явной версией, именем TUN, списками **точных IPv4/IPv6-хостов**, обязательной защитой обычного DNS. CIDR и произвольные правила nftables не принимаются.
- Имя интерфейса разрешает только ASCII буквы/цифры/символы "_" и "-"; строки JSON не выполняются в shell.
- Правила создаются одной атомарной транзакцией nft. Используется собственная таблица inet fedup_lab_guard; существующие системные таблицы не изменяются, flush ruleset не вызывается.
- Повторная установка поверх существующей таблицы запрещена. Команда `ensure` идемпотентна: при повторном запуске сервиса она проверяет существующие правила, не заменяя их; при обнаружении изменений возвращает ошибку и ничего не переписывает. Проверка verify сравнивает полную ожидаемую цепочку правил, игнорируя только значения динамических счётчиков.
- Явное удаление разрешено только после проверки целостности и с флагом --confirm-lab-remove. При ошибке правила не удаляются автоматически — запрет сохраняется.
- Нет фонового демона, правки системных маршрутов, глобального firewall, NAT, автоматического восстановления после перезагрузки, защиты DNS-over-HTTPS, приложения Android или Windows.
- Netguard не защищает ни от изменения правил администратором с root, ни от утечек по адресам, которых нет в конфигурации.

## Формат лабораторной политики

~~~json
{
  "version": 1,
  "tun": "futclient",
  "protected_ipv4": ["10.88.0.10"],
  "protected_ipv6": ["fd42:fed1::10"],
  "block_plain_dns": true
}
~~~

В этой версии перечисляются только **точные** адреса удалённого тестового узла. Для настоящего полного VPN потребуется другая модель разрешений, исключение маршрута до входного VPN-сервера, policy routing, системный DNS и контроль IPv6/приложений.

## Проверка на Debian/MX Linux

~~~bash
sudo apt install nftables iproute2 iputils-ping curl python3 \
  openssl libssl-dev pkg-config tcpdump
cd ~/git/fedup
git pull
cargo build --workspace
cargo test --workspace --all-targets

# Только временные Linux network namespace, без изменения хоста
sudo env FEDUP_TUN_TRANSPORT=raw FEDUP_TUN_FAULT=1 bash tests/tun-smoke.sh
sudo env FEDUP_TUN_TRANSPORT=h2 FEDUP_TUN_FAULT=1 bash tests/tun-smoke.sh
~~~

Скрипт сам создаёт временные ключи, netguard.json, сетевые пространства и обходной маршрут. Он доказывает, что обход реально работает **до** установки правил; затем с помощью netguard устанавливает запрет и проверяет IPv4/IPv6, TCP/UDP/DNS и передачу большого файла с эмуляцией потерь. После аварии клиента таблица продолжает блокировать прямой путь. Тест дополнительно проверяет запрет повторной установки, обнаружение постороннего правила и явное удаление в конце.

Для будущего безопасного перезапуска системного сервиса предусмотрена команда `fedup-netguard ensure /path/to/netguard.json`: она создаёт таблицу при отсутствии, а если таблица уже существует, требует её полного соответствия конфигурации. Она **не** выполняет автоматический небезопасный сброс изменённых правил. Сейчас этот механизм разрешён только в сетевом пространстве лаборатории.

Чтобы получить только текст плана (никаких изменений сети), можно использовать команду fedup-netguard plan /path/to/netguard.json, но **не запускайте сгенерированные nft-правила на рабочем хосте**.

## Что нужно для рабочего Linux-клиента

1. Отдельный минимально привилегированный системный агент с ограниченным IPC, который не принимает произвольные команды nft от клиента.
2. Настройка policy routing и безопасного маршрута к VPN-серверу, установка защищающих правил **до** открытия маршрутов с возможностью прямого выхода.
3. Чёткая политика DNS/IPv6 и разделения приложений: какие пакеты под защитой, а какие могут выходить напрямую.
4. Идемпотентные обновления, журнал восстановления, атомарный откат, сохранение политики при сбое самого агента.
5. Приёмочные испытания с NetworkManager, существующим nftables/iptables, одновременно подключёнными VPN и сменой внешней сети.
6. Отдельная безопасная подготовка DEB, systemd, ручная аварийная процедура восстановления и ревью до установки на реальный ПК.
