# FedUp — клиентские ключи и регистрация на Linux

Появилась первая программа **fedup-device**: создаёт собственный ключ P-256 на клиентском компьютере, шифрует его в PKCS#8 и формирует подписанный запрос CSR по одноразовому приглашению. Администратор получает только CSR и не видит закрытый ключ.

Это лабораторная Linux-версия, а **не полноценный VPN** и не готовое приложение Android. Ключ хранится в зашифрованном файле и открывается паролем при запуске, без зависимости от GNOME Keyring/KWallet. Устройство с отсутствующим или повреждённым файлом ключа не подключится, открытый ключевой файл не подставляется автоматически.

## Полный цикл регистрации

Сначала на изолированной машине администратора создаётся приглашение через fedup-enroll, как описано в [инструкции по выдаче приглашений](enrollment.md). Файл приглашения доставляется пользователю **по доверенному каналу**: он содержит одноразовый токен.

На клиенте:

~~~bash
cargo build -p fedup-identity
target/debug/fedup-device request phone-invite.json ./my-phone ./phone-request.json
~~~

Программа попросит ввести и подтвердить пароль для шифрования ключа. Требуется не менее 16 байт UTF-8. Пароль не передаётся через аргументы командной строки. Будет создан приватный каталог my-phone с файлами:

~~~text
my-phone/
  client-key.enc.pem    # зашифрованный ключ PKCS#8, права 0600
  client.csr.pem        # публичный запрос на подпись
  ca.pem                # CA из приглашения
  device.json           # имя устройства, pin CA, имя сервера; без токена
~~~

Файл phone-request.json находится отдельно и **содержит секретный одноразовый токен**. Его нужно передать администратору приватно и не коммитить в GitHub.

Администратор проверяет заявку и офлайн подписывает CSR. Из-за отсутствия защищённого CA-хранилища нынешняя лабораторная команда подписания требует флаг unsafe-lab-plaintext-ca. На реальной инфраструктуре использовать этот режим нельзя. Затем администратор добавляет подписанный сертификат в список разрешённых через fedup-admin.

Получив сертификат на клиенте:

~~~bash
target/debug/fedup-device import ./my-phone ./phone-issued.pem
~~~

Проверяются действительность сертификата, подпись CA, назначение для TLS-клиента, имя устройства и соответствие локальному закрытому ключу. Только после этого сертификат записывается в my-phone/client.pem.

## Подключение к экспериментальному TCP-транспорту

Для собственного испытательного сервера в частной лабораторной сети:

~~~bash
cargo build -p fedup-link
target/debug/fedup-link client-device 127.0.0.1:8000 SERVER_IP:PORT ./my-phone
~~~

Программа самостоятельно берёт имя сервера и закреплённый CA из my-phone и просит пароль, чтобы разблокировать зашифрованный ключ в оперативной памяти. Никакой файл с открытым ключом не создаётся. Сервер по-прежнему пересылает соединения только к заранее настроенному локальному сервису, а не маршрутизирует весь интернет.

Синтаксис с явным unsafe-lab-plaintext-key сохранён **только для старых стендовых тестов**. В обычном клиентском режиме открытый ключ не принимается.

## Автоматическая проверка на Debian / MX Linux

Понадобятся Rust/Cargo, pkg-config, заголовки OpenSSL (в Debian пакет libssl-dev), Python 3 и openssl:

~~~bash
git pull
cargo build --workspace
cargo test --workspace --all-targets
bash tests/device-smoke.sh
~~~

Скрипт создаёт одноразовые тестовые сертификаты, регистрирует устройство, проверяет правильный/неправильный пароль, отказ в импорте чужого сертификата и передачу реальных бинарных данных через mTLS. Все временные ключи удаляются после испытания.

## Ограничения безопасности

- Здесь реализован **зашифрованный файл**, а не интеграция с TPM, KWallet, Secret Service, Android Keystore или Windows CNG. Если пользователь теряет пароль, ключ не восстанавливается и устройство требуется зарегистрировать заново.
- Парольный механизм PKCS#8 использует стандартную реализацию OpenSSL. Устойчивость KDF к перебору и политика разблокирования требуют дополнительной оценки перед релизом.
- Разблокированный ключ существует в памяти процесса в течение работы TLS-клиента; аппаратной изоляции нет.
- Само приглашение не подписано отдельным доверенным ключом. Защищённость его CA pin зависит от **доверенной доставки**.
- Автоматической доставки сертификата и приглашения пока нет, равно как TUN, DNS, UDP, IPv6 и публичного безопасного сетевого сервиса.
- Трафик нашего TCP-транспорта **не имитирует HTTP/2/HTTPS**. Обнаруживаемость и устойчивость к блокировкам ещё не измерялись.

Основная цель этой версии — доказать, что секрет устройства можно создать локально, выпустить сертификат по CSR и реально подключиться без передачи закрытого ключа администратору.
