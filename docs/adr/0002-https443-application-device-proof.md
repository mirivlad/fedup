# ADR-0002 — HTTPS на одном 443 и подтверждение устройства внутри приложения

**Статус: экспериментальный прототип реализован и проверяется в изолированных Linux network namespaces; production-приёмка НЕ выполнена.**
**Дата: 10 ноября 2026.**
**Применимость: исследовательский этап 3, без ослабления защищённости FedUp.**

## Проблема

В нынешнем FedUp API учётных записей публикуется через Caddy HTTPS на TCP 443,
а HTTP/2 IP-туннель слушает отдельный TCP 7443. TLS-рукопожатие туннеля
использует запрос клиентского сертификата. Даже с введённым обычным HTTPS
fallback анонимный активный зонд может заметить запрос сертификата.
Отдельный порт 7443 также остаётся открытым наблюдателю.

Общий браузероподобный ClientHello, отсутствие явных отличий при активной
проверке, многопользовательский IP-туннель и надёжная авторизация — отдельные
требования. Подмена TLS-реквизитов сама по себе не делает трафик
неотличимым от браузерного.

## Решение для следующей экспериментальной версии (не включать по умолчанию)

1. **Один публичный HTTPS TCP 443.** Caddy продолжает обслуживать
   действительный сайт и обычные API. Транспорт IP-пакетов допускается
   лишь через ограниченный внутренний HTTP/2 stream-обработчик.
   Upstream слушает только loopback / Unix socket, не создаёт второго
   общедоступного TLS-порта. Проверить, что reverse_proxy не буферизует
   двустороннее DATA до закрытия HTTP/2 POST.
2. **Обычный публичный TLS.** Транспортный фронт не требует и не предлагает
   клиентский сертификат в TLS-рукопожатии. Защиту HTTPS обеспечивают
   штатный публичный сертификат и TLS 1.3; TLS 1.2 можно использовать
   лишь после отдельного анализа совместимости и настроек Caddy.
   Не пытаться подделывать TLS/HTTP ответы вручную.
3. **Внутренняя проверка устройства по доказательству владения ключом.**
   Пользователь по-прежнему вводит только *домен, логин, пароль*.
   Android генерирует неэкспортируемый P-256 ключ и автоматически получает
   подписанный краткосрочный сертификат после входа. На HTTP/2 уровне
   клиент сначала получает случайный одноразовый серверный challenge
   и подписывает каноническое представление: версия протокола,
   назначение ключа (device-auth), идентификатор узла/соединения,
   challenge, случайный nonce клиента, метод и путь защищённого запроса.
   Сервер проверяет подпись публичным ключом сертификата и его цепочку,
   срок, EKU, текущий account revision и отзыв в базе. **Запрос без подписи
   никогда не создаёт TUN, не допускается к маршрутизации и не получает
   данных или признаков существования учётной записи.**
4. **Защита от replay и путаницы контекстов.** Challenge должен быть
   непредсказуемым (криптографический RNG), однократным, краткосрочным,
   ограниченным по памяти и привязанным к контексту подтверждаемого
   защищённого сеанса. Обязательно проверить повтор подписи на ином
   сеансе, смену пользователя, другого узла, истечение challenge,
   отзыв устройства и гонки. Рассмотреть доступную через фронт
   экспортируемую привязку TLS-канала и запретить подписывать один
   контекст для другого назначения.
5. **Не использовать пароль в транспортных пакетах.** Пароль относится
   к enrollment API; долгоживущий VPN подтверждает ключ устройства.
   Не вводить общие статические bearer-токены как замену этому
   подтверждению без отдельной модели компрометации.
6. **Внутренний upstream.** Даже если proxy terminates TLS, upstream должен
   быть изолирован, иметь ограничения соединений и запросов,
   не доверять клиентским заголовкам авторизации без подтверждения,
   не допускать подмены forwarded IP/TLS metadata.
7. **Никаких утечек при переходе.** До успешного ответа сервера не объявлять
   Android VPN подключённым. Не удалять уже работающее защитное правило
   при ошибке. Существующий mTLS остается лабораторным режимом до
   независимой проверки нового пути.

## Обязательные испытания

- Изолированный Caddy/HTTPS2 фронт + статический веб-сайт + HTTP2 duplex VPN.
  GET / должен быть обычным сайтом, а без device proof IP-трафик запрещён.
- Неправильная подпись, чужой CSR/ключ, replay, просрочка, отзыв устройства,
  повторное использование nonce, перезапуск issuer, 32+ незавершённых
  клиентских соединения — **fail closed** без утечек и DoS бесконечными сессиями.
- Сравнение с настоящим HTTPS/2 от Chromium/Firefox и Android на **том же
  TCP 443**, одинаковой имитируемой нагрузкой; разделить данные обучения
  и тестирования по независимым соединениям. Записывать как истинные
  срабатывания, так и ложные срабатывания на легитимные веб-клиенты.
- Проверка длительных соединений, многопоточного HTTP, MTU,
  UDP DNS, аварий, повторных подключений и честного закрытия HTTP/2.
- Обычную доступность сайта и корректность TLS/сертификата не нарушать.

## Почему пока не выполнено

Нынешняя схема с TLS mTLS использует проверенный verifier rustls
и привязку сертификата к реальной учётной записи. Нельзя просто выключить
TLS-проверку и доверять полю fingerprint в HTTP-запросе: любой клиент мог бы
подставить чужой fingerprint и получить чужой TUN. До появления
полноценного proof-of-possession и тестов старый защищённый путь остаётся.

## Важное ограничение

Успех этих испытаний — снижение *измеренных отличий от контрольного HTTPS*,
а не доказанная «невидимость для РКН». Адрес сервера и некоторые
метаданные всё равно наблюдаемы; доступность при IP/ASN блокировке
не гарантирована.
